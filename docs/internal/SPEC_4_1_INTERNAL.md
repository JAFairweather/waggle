# §4.1 (internal, v1.9) — Granted external participants

### 4.1 Granted external participants — the second inbound tier (Phase-3.5)

§4 governs the *anonymous* door: strangers are quarantined until a human approves them. This section adds the opposite tier — a **known external identity admitted as a first-class, self-signed participant** under a scoped, revocable grant. Its writes skip the quarantine queue; where the channel is sealed, the grant also conveys the read capability so the identity opens the conversation with its **own** key. Where §4 keeps strangers out until vetted, §4.1 lets a vetted identity in on a leash the maintainer can drop. The motivating target is an agent that holds its own Nostr key and interacts through a general Nostr MCP, administered entirely from a UI, party to a community's conversations *as itself* — a materially stronger consumer of the delegation primitive than the moderation lane, because the grant can convey genuinely private content, not just authority to act. <!--INT-->(Concretely for us: bringing Claude into Buzz as head of development for the team's research and spec authorship, via Waggle + a Nostr MCP — James, 2026-07-29.)<!--/INT-->

**The load-bearing correction — verify the *substrate* before the mechanism.** The design converges on a Concord read-capability (a sealed grant the participant decrypts with its own key). That machinery is correct — but it answers only one of **three distinct substrates**, and the read primitive, the grant's role, and the revocation story differ across all three. Conflating them is the frame error: the mechanism debate was rigorous inside the wrong frame for the literal target. Ground-truthed 2026-07-29 (`buzz channels members` returns a pubkey-keyed roster; every event in the team's native working channels is `kind:9`, plaintext, `auth`-tagged — not a sealed plane):

| # | Substrate | Content | Read primitive | Grant's role |
|---|-----------|---------|----------------|--------------|
| **S1** | Native Buzz `kind:9` working channels (pubkey-keyed membership) | **Plaintext to members** | Membership + fleet-relay NIP-42 auth | Public governance paper over native membership — **no encrypted body** |
| **S2** | Concord sealed-plane community (`kind:1059` under the plane pubkey) | Encrypted | Concord read-cap the participant decrypts with its own key | Conveys a **Private-channel `(key, epoch)`** — the real encrypted body |
| **S3** | Public `kind:1` (the existing in-door, §3.3) | Already public | Auto-promote past the §4 quarantine | Public admission credential |

**Clean line: admission facts are public on every substrate; encrypted-content delivery exists on S2 only.** Below, each mechanism is tagged with the substrate it governs, so an implementer never applies a Rekey to S1 (meaningless) or omits it on S2 (silent read-persistence).

**Headline demo — S2, an encrypted-body reference implementation (James's call, 2026-07-29).** Named explicitly, because the substrates make materially different reference-implementation claims. On **S2** the grant conveys something genuinely private — a read capability into a sealed community — so it is the **first honest consumer of NIP-DA's actual `kind:30440` encrypted body**, not merely its grant/revoke lifecycle (the moderation lane in §4 borrows the lifecycle only, deliberately). That is the dogfood #2411 has lacked. **S1 falls out of the same machinery for free:** the identical admin UI issuing the identical public grant, but over native Buzz membership — the *simplest* of the three (add the key to the channel roster, its MCP NIP-42-auths to the fleet relay, reads and writes native `kind:9`), no Concord, no mirror, honest instant revoke — with the honest caveat that on S1, NIP-DA shrinks to auditable governance paper, **not** the body-consumer claim. One UI administers both; S2 is the headline, S1 the simplest included case.

**Consumption seam — resolved for the external MCP identity, and honestly scoped (S2).** The internal lane could never consume a scoped grant: fetches 403 on p-gated kinds (stale relay auth) and the buzz-acp harness never pipes grants into an agent's context (`RESEARCH/GRANT_CONSUMPTION_PATHS.md`). An **external MCP identity — one holding its own key via a general Nostr MCP — escapes both** <!--INT-->(the target case: a Claude-administered identity)<!--/INT--> — it holds its **own** key (so it decrypts the `kind:30440` body itself) and its **own** relay auth through the MCP server (so no 403), and there is **no harness in the path** — the MCP tool surface *is* the ingestion handler. Both blockers clear precisely where the internal lane failed both. This is what makes S2 buildable now. **On S1 the seam is moot** — the content is plaintext, there is no grant body to fetch or decrypt; the identity needs membership + relay auth, not decryption. So the "first honest #2411 *encrypted-body* consumer" claim is **true on S2 and false on S1** — the reason S2 is the headline.

**Non-custody — holds on every substrate; the seam lives in one word (Dennis's stress-test).** §3.1 (the bridge never decrypts) stays pristine throughout: on **S1** trivially (plaintext to members; the bridge need not be in the read path at all — the participant REQs `kind:9` by channel directly once authed); on **S3** nothing is sealed. On **S2** it holds **iff "mirror" means byte-verbatim `kind:1059` rebroadcast, never a re-seal.** An implementer told to "deliver to the participant's inbox" will reach for decrypt-then-reseal-to-its-key by reflex — that is the rejected custodial path. The wrap must stay sealed under the plane pubkey; the participant opens it with the channel key the grant conveyed. Cleaner still where the relay allows it: **no mirror at all** — the participant holding the channel key holds the plane pubkey and REQs `{kinds:[1059], authors:[<plane_pk>]}` directly. Either way, **zero decrypt by the bridge.**

**Revocation — the write/read split, refined per substrate.** "One grant, pulling it is instant de-authorization" is only half true, and the half that fails is the dangerous one to advertise:
- **S1 — instant and symmetric.** A `441` revocation drops the key from the membership roster; the fleet relay stops serving it read and quarantines its next write. No key was handed out to keep decrypting, so **no Rekey is needed and no read-revocation theater exists** — the cleanest revocation of the three, and a real reason S1 is attractive.
- **S2 — the split is real.** Write-revoke is instant (441, bridge-enforced at the quarantine gate). **Read-revoke is theater until a Concord single-channel Rekey rotates the key out** — a removed holder still holds a valid key and keeps decrypting; holding a key is never authority. The UI "revoke" must therefore fire **both** the 441 **and** the matching Concord Rekey, and report "read de-authorized" **only after the Rekey confirms.** S2 read grants belong on **Private** Concord channels only (single-channel Rekey is cheap and narrow); on a **Public**, community-root-derived channel the only read-revoke is a whole-community **Refounding** — effectively irrevocable — and the UI must refuse to imply otherwise.
- **S3 — write-revoke instant (441); no read to revoke** (already public).

**The admin UI (the product James asked for).** Its core object is a **per-identity trust record** with (a) an **admission-mode toggle** — quarantine (§4, message-by-message) ⇄ standing grant — and (b) a **channel-scope selector** (scope strings carry a *hash* of the channel id, never the raw UUID, since these events may ride public relays). It is a **grant/approval console** that signs NIP-DA events (440 issue / 441 revoke / 10440 index) under the maintainer key and publishes them; the bridge consumes them exactly as §4 Phase 3 already specs — so the admin surface needs **zero** broken-consumption dependency. Because authority moves as signed events, **the UI is fully decoupled from the box** (it cashes out the co-location dissolution §4 already won) and can live as a Buzz Desktop panel. The e2e loop, one clean authorization: the maintainer issues a scoped grant in the UI → it conveys admission (public, bridge-verifiable) and, on S2, the read cap (private, to the participant's key only) → the participant's MCP reads the granted channels with its own key (bridge never decrypts) → it posts back **signed as itself**, auto-promoted past quarantine → it reads and writes as a first-class signed participant. No nsec is ever shared; one grant is the whole authorization; a 441 (plus Rekey on S2) is de-authorization.

**A8 is the hard gate on the write half.** Across every substrate, without native foreign-signed rendering the participant's writes render **re-authored under the operator key** (§3.3) → ghost-written, not "directly party," and they re-inherit the §3.3 **B-2 Terms rights-exposure**. **A8** makes the participant appear **as itself, self-signed, `bot: true`** and simultaneously resolves that Terms clause — identity fidelity and the rights fix in one platform change. A8 is a **Buzz-platform ask** (§3.3, currently slated Phase 4), so §4.1's write half has a hard external gate: until A8 lands, the loop runs in a **degraded mode** — reads work (path A works today), but writes render re-authored with the interim structured `q`+`p` tags. Demoable, not the full vision. **This use case is the strongest argument yet to pull A8 forward** from Phase 4; sequence it that way — the grant/UI/read half is ours to build now, the "as itself" write half is gated on Buzz.

**Provisional-kind versioning (extends the §4 config constant).** §4/§6 already hold 440/441/10440 behind a single config constant (Marmot 44x band; fiatjaf typically renumbers at merge — `RESEARCH/NIP_DA_MERGE_PATH_2411.md`). §4.1 adds surface that constant must also cover: the **S2 read-grant body kind (`30440`)**, the hashed-channel scope-tag name, and the admission-vs-read capability discriminator — all behind the *same* knob, so a merge-time renumber stays a one-line rev. Separately flag the **Concord coupling**: S2 read-revocation depends on the Concord Rekey format + channel-epoch semantics, which are Concord's to version, not NIP-DA's — a Concord rekey-format change would silently break read-revocation if unlinked.

**One open experiment gates S1.** Whether the auth-gated fleet relay serves an **external, non-Desktop-managed key** that NIP-42-authenticates and is added to a channel roster is **unverified** — it 401s strangers (§3.5), but NIP-42-auth-as-membership vs a Desktop-managed allowlist is untested for it. Concrete spike: auth a fresh external key added to a test channel roster, REQ `kind:9` by channel, confirm events return. If it will not serve an external member key, **S1 falls back to a bridge that mirrors plaintext `kind:9` to a relay the participant can read** — still zero-decrypt, non-custody intact.
