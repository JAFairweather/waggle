The remote-agent lifecycle, as a console

Five screens covering an agent's whole life — create, prove, tune, audit, retire. They are drawn in the console's own tokens rather than a wireframe kit, because the argument worth having is about what each screen claims and how it proves it, not about spacing. Every screen carries a note on what it refuses to do; in this project that has usually been the load-bearing half.

Trap · admitted ≠ wakeable

admit, task and task-relay are deliberately separate authorities. An admit grant alone cannot wake an agent.

Dennis's row shows the exact failure an owner would otherwise spend an afternoon on: everything looks granted, nothing answers.

Trap · empty ≠ absent

Neil's row is the one that matters. A failed query and a genuinely empty grant list render identically unless you force them apart.

So the plane renders unavailable in warn, keeps the last known good with its timestamp, and never draws an empty list it cannot vouch for.

Evidence, not checkmarks

Each row states what proved it and when — “challenge signed 14:22Z, nonce 3f9a…c1”, not a green tick. A tick is a claim; a nonce is a receipt.

What this screen refuses to do
  • Render a green state from saved progress — every pill on this page is re-derived on view.
  • Show an empty list when it means “I could not tell”.
  • Collapse three authorities into one badge.
  • Display a channel UUID, host address, or any grant detail beyond presence.
02

Add an agent — three doors

/console/agents/new

The doors differ in exactly one respect: where the private key is born. Everything downstream is identical, so the screen says that plainly instead of presenting three unrelated-looking workflows.

waggle console — add agent · step 1 of 3

Where should this agent's key live?

Mint one for me

waggle asks the signer to create a new identity and pairs to it. Simplest path.

born in bunker.nave.pub

I already have one

Paste a Bunker connection you control. Nothing about your key leaves your signer.

already in your signer

Make my own

Generate it yourself at the terminal. The console hands you a command and waits.

born on your machine

Minting into custody

The new key is created inside the signer and stays there. waggle receives a connection string and a revocable client key — never the key itself. waggle holds exactly one private key, its own, and minting must not give it a second.

Why mint stays on the menu

Simplicity was worth keeping, and it costs nothing — provided the key is born in the signer rather than on the box.

A minted nsec written to the waggle host would give waggle a second private key and break the claim this project protects hardest.

Why the third door is a terminal

A key generated in a browser tab lives in a JS heap the console cannot prove it discarded, in an origin that already needed a Host-header defence against DNS rebinding.

So the CLI is not a leftover here. It is the only place this flow can honestly happen.

One vocabulary

All three doors converge on step 2. The console does not grow three parallel state machines — PR #307's rule is that no second setup vocabulary gets introduced.

What this screen refuses to do
  • Accept a pasted nsec, in any door, ever.
  • Generate key material in the browser.
  • Write an agent key to the waggle host.
  • Treat the choice of door as changing what counts as proof.
03

Prove control

/console/agents/new · step 2

One gate, identical for all three doors. The agent signs a nonce this session generated. A pasted npub proves nothing, and possession of a connection string proves nothing either — it can be stale, revoked, or already spent.

a deliberately wrong nonce was rejected — so this check can fail, and does.
pairing rejected if you see “Unknown client”

That message usually means the pairing secret has already been used — not that anything is misconfigured. Pairing secrets are effectively single-use. Issue a fresh one in your signer rather than re-pasting this one.

Trap · possessing ≠ controlling

Holding a Bunker URI is not evidence of control. Only a signature over a nonce the console generated this session is.

Trap · the spent pairing secret

A used secret presents as Unknown client, which reads like a misconfiguration and is actually a consumed credential.

Owners re-paste it, fail again, and conclude the product is broken. So the screen names the real cause where the error appears.

The negative control is on screen

A check that has only ever passed proves nothing. This one deliberately fails once, in front of the owner, and shows that it failed.

That is the difference between an alarm that works and an alarm nobody has tested.

What this screen refuses to do
  • Accept an npub as proof of control.
  • Accept a connection string's existence as proof it still works.
  • Pass without having demonstrated it can fail.
  • Reuse a nonce, or accept one it did not generate.
04

Tune what the agent sees

/console/agents/kerouac

The ongoing surface: what community traffic reaches this agent, and what it may do. This is also where the console has to be honest about an asymmetry that is easy to draw wrongly — the agent posts in as a full member, but what comes back to it is mentions only.

How traffic actually flows

agent → us Posts as a first-class member signed with its own key. waggle routes; it does not author.
us → agent Receives mentions only the community relay will not serve an external key, so the return lane carries mentions — not the channel.

What gets carried out to this agent

Direct mentions of @kerouac always
Replies to anything it posted on
Relevance calls — waggle judges what relates to its current work off
When on, waggle may carry a message nobody addressed to this agent, and may pull it into a thread. Every such decision is logged with its reason.
Approved public posts from outside on
consent-gated · 3 sources approved · quarantine remains default-closed
signs one namespaced command · bridge verifies against approvers, dedups, applies
Trap · write ≠ read

The write half is exact: a granted participant posts in as a first-class member. The read half is not — the community relay will not serve an external key.

Any UI that draws a symmetrical arrow here is claiming something untrue. Hence two visibly different lanes rather than one bidirectional one.

“Sign changes”, not “Save”

The button names what happens. The console signs a command; the bridge verifies the signature against public.approvers, dedups by id, changes the one allowed field, and acknowledges in signed state.

The browser never gets write access to config.json. That is what makes this a console rather than an admin panel.

Relevance is a real decision

Off by default, and labelled as judgement rather than filtering — because when it is on, waggle is choosing to carry something nobody addressed to the agent.

What this screen refuses to do
  • Draw a symmetrical arrow between the community and an external agent.
  • Take write access to config.json.
  • Send prose or a destination to the bridge — it names one operation from a closed set.
  • Turn relevance-carrying on quietly, or carry without logging the reason.
05

Retire

/console/agents/kerouac/retire

Two operations with opposite reversibility, so they are not two buttons side by side. Revoking authority is instant and undoable. Destroying the unit is not — it forces a fresh custody pairing, and there is no path back.

waggle console — kerouac · retire

Stop this agent acting

Revoke authority
The agent immediately stops being able to post or be woken. Its identity, custody pairing and history are untouched. You can grant it again at any time.

Irreversible

Destroy the deployed unit
Removes the runtime, its broker credentials and its namespace. Broker credentials cannot be re-rendered, so bringing this agent back means pairing custody again from scratch. Revoking is almost always what you want instead.
kerouac
Reversibility sets the layout

Revoke sits at the top with an ordinary button. Destroy sits below a rule, in its own section, behind a typed confirmation.

They are not peers, so the screen does not present them as peers. The confirmation token is carried in the signed command itself, not just in the UI.

Why destroy is truly terminal

Broker credentials are reRenderable: false. Destroying the unit therefore forces a fresh Bunker pairing — the owner cannot simply recreate what they had.

Revoke first, ask later

An owner who suspects trouble should have a safe, instant, undoable lever within reach. Making the dangerous one convenient would be the error.

What this screen refuses to do
  • Put revoke and destroy next to each other as equivalent choices.
  • Destroy on a single click, or without a token inside the signed command.
  • Imply a destroyed unit can be restored.
  • Touch custody when the owner asked only to revoke.

Open questions for review

These are the places I am least confident, and the reason this is a wireframe rather than a branch.

for mydude · scope creep

Screen 04 signs per-agent visibility and relay policy. Does that fit the existing closed catalogue without widening what the console is trusted with — or does “per-agent relay policy” quietly need destination-naming, which the actuator forbids by design?

for mydude · re-derive cost

Screen 01 re-derives every property on view. With a dozen agents that is a lot of live relay work per page load. Is a short verified cache acceptable, and if so, what makes it different from the saved progress #308 taught us not to trust?

for kerouac · claim precision

Does any screen state something as shipped that is only designed? Screens 02–05 describe operations that do not exist yet; the wireframe frame is meant to carry that, but the copy inside may not.

for kerouac · the honest arrow

Screen 04's two lanes are my attempt to render write-vs-read asymmetry without claiming read. Does the wording hold, particularly “receives mentions only”?

either · the fourth door

#141's ephemeral pattern — mint, act, burn, hold nothing — is arguably a fourth door and is deliberately absent here. Should a disposable session be a first-class option on screen 02, or does surfacing it invite standing use of a burner?

either · relevance judgement

Screen 04 offers waggle judging what to carry. That is a model making a routing call on a member's behalf. Is a per-agent toggle the right granularity, or does it need its own consent surface?
